# RAG Bot — Веб-приложение с диалоговым интерфейсом

Веб-приложение для диалога с RAG-ботом (Retrieval-Augmented Generation). Бот ищет информацию в базе знаний, формирует ответы с помощью языковой модели, кэширует повторяющиеся запросы и записывает все взаимодействия в SQLite для мониторинга и анализа.

## Описание проекта

**RAG** — технология, объединяющая поиск информации в базе знаний с генерацией текста на основе языковых моделей. Приложение находит релевантные фрагменты в документах и использует их для формирования точных ответов.

### Возможности

- **Диалоговый интерфейс** — веб-чат в браузере
- **RAG-запросы** — поиск и ответы на основе базы знаний
- **Векторный поиск** — семантический поиск через FAISS
- **Умный сплиттинг** — разбиение документов по абзацам, длинные абзацы — по предложениям, с overlap 20%
- **Кэш ответов (SQLite)** — повторный запрос с тем же текстом отдаётся из `data/cache.db` без эмбеддинга, FAISS и LLM
- **Журнал взаимодействий (SQLite)** — каждый запрос пишется в `data/logs.db`: вопрос, ответ, источники, сессия, попадание в кэш, время ответа
- **Экспорт логов** — CSV для анализа в Excel или подготовки датасета
- **Память диалогов** — до 10 пар сообщений (user/assistant) для контекстных ответов
- **Индексация документов** — загрузка и переиндексация `.txt` файлов
- **Два провайдера LLM** — ProxyAPI (основной) и GigaChat (альтернативный)

## Провайдеры LLM

### ProxyAPI (основной)

OpenAI-совместимый HTTP endpoint. Используется по умолчанию (`LLM_PROVIDER=proxy`).

**Преимущества:**
- Работа с OpenAI-совместимыми API
- Полный контроль над HTTP-запросами
- Поддержка GPT-моделей для чата и эмбеддингов

**Модели по умолчанию:**
- Чат: `gpt-4o-mini`
- Эмбеддинги: `text-embedding-3-small`

### GigaChat (альтернативный)

LLM от Сбера. Включается через `LLM_PROVIDER=gigachat`.

**Преимущества:**
- Российский провайдер
- Встроенные эмбеддинги
- Не требует зарубежных API-ключей

**Модели по умолчанию:**
- Чат: `GigaChat`
- Эмбеддинги: `Embeddings`

> **Важно:** у каждого провайдера свой FAISS-индекс (`index_proxy.faiss` / `index_gigachat.faiss`). При смене провайдера выполните индексацию заново.

## Установка и настройка

### Требования

- Python 3.10+
- API-ключ ProxyAPI **или** GigaChat

### Шаг 0: Клонирование репозитория

```bash
git clone https://github.com/BeastHealer/rag_memory_system.git
cd rag_memory_system
```

### Шаг 1: Установка зависимостей

```bash
cd web
python -m venv venv

# Windows
venv\Scripts\activate

# Linux / macOS
# source venv/bin/activate

pip install -r requirements.txt
```

### Шаг 2: Настройка переменных окружения

Скопируйте `example.env` в `.env` (в корне проекта или в `web/`) и заполните значения:

```bash
cp example.env .env
```

**Для ProxyAPI (основной):**

```env
LLM_PROVIDER=proxy
PROXY_API_URL=https://api.proxyapi.ru/openai/v1
PROXY_API_KEY=your_proxy_api_key_here
```

**Для GigaChat (альтернативный):**

```env
LLM_PROVIDER=gigachat
GIGACHAT_CREDENTIALS=your_gigachat_credentials_here
GIGACHAT_VERIFY_SSL_CERTS=false
```

### Шаг 3: Подготовка документов

Добавьте `.txt` файлы в директорию `data/docs/` (кодировка UTF-8).

## Запуск

Из каталога `web/`:

```bash
cd web
python app.py
```

Или из корня проекта:

```bash
python web/app.py
```

Откройте в браузере: [http://127.0.0.1:8000](http://127.0.0.1:8000)

### Первый запуск

1. Откройте веб-интерфейс
2. Нажмите **📥** (Индексация) для загрузки документов в базу знаний
3. Начните задавать вопросы в поле ввода

## Использование

### Интерфейс

| Элемент | Описание |
|---------|----------|
| Поле ввода | Задайте вопрос и нажмите Enter или ➤ |
| 📥 | Индексация документов из `data/docs/` |
| 📊 | Статистика системы (включая число записей в кэше) |
| 🔌 | Проверка подключения к API |
| 🧹 | Очистка истории текущего диалога |

### Пример диалога

```
👤 Что такое RAG?

🤖 RAG (Retrieval-Augmented Generation) — технология, которая объединяет
   поиск информации в базе знаний с генерацией ответов...
   📚 Источники: FAQ.txt

👤 А где это используется?

🤖 RAG активно используется в службах поддержки, HR-отделах,
   технической документации...
   📚 Источники: FAQ.txt, IZP.txt

👤 Что такое RAG?

🤖 ...тот же ответ мгновенно...
   📚 Источники: Кэш (SQLite)
```

Повторный вопрос с тем же текстом отдаётся из SQLite-кэша: этапы эмбеддинга, поиска в FAISS и вызова LLM пропускаются. И кэш-хит, и полный RAG-ответ всё равно записываются в журнал `logs.db`.

### Журнал и экспорт

Метрики журнала:

```bash
curl http://127.0.0.1:8000/api/logs/stats
```

Пример ответа:

```json
{
  "total_interactions": 42,
  "cached_interactions": 11,
  "unique_sessions": 3,
  "cache_hit_rate": 0.2619,
  "avg_response_time_ms": 840
}
```

Скачать CSV:

```bash
curl -O -J http://127.0.0.1:8000/api/logs/export
```

Колонки CSV: `id`, `timestamp`, `session_id`, `query`, `response`, `source`, `from_cache`, `response_time_ms`.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/` | Веб-интерфейс чата |
| POST | `/api/chat` | Отправить сообщение |
| POST | `/api/ingest` | Индексация документов |
| POST | `/api/clear` | Очистить историю сессии |
| GET | `/api/stats` | Статистика RAG (в т.ч. `cached_queries`) |
| GET | `/api/test` | Проверка API |
| GET | `/api/logs/stats` | Метрики журнала взаимодействий |
| GET | `/api/logs/export` | Скачать `logs.csv` |

**Пример запроса:**

```bash
curl -X POST http://127.0.0.1:8000/api/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "Что такое RAG?", "session_id": null}'
```

**Пример ответа:**

```json
{
  "answer": "...",
  "sources": ["FAQ.txt"],
  "session_id": "uuid",
  "model": "gpt-4o-mini",
  "from_cache": false,
  "response_time_ms": 1840
}
```

При попадании в кэш: `"model": "cache"`, `"from_cache": true`, `"sources": ["Кэш (SQLite)"]`. Время ответа при этом обычно значительно меньше.

## Технические детали

### Архитектура

```
Пользователь → Веб-интерфейс (FastAPI)
                    ↓
              RAG Pipeline
                    ↓
              SQLite Cache (cache.db)
             /                      \
          hit                        miss
           ↓                          ↓
        ответ                  Retriever (FAISS)
                               + LLM Provider
                                      ↓
                               ответ → запись в кэш
                    ↓
         DatabaseLogger (logs.db)
         вопрос, ответ, источники,
         session_id, from_cache, response_time_ms
```

### Компоненты

| Компонент | Описание |
|-----------|----------|
| **app.py** | FastAPI, умный сплиттинг, сессии диалога, замер времени, запись в журнал |
| **db_logger.py** | SQLite-журнал взаимодействий и CSV-экспорт |
| **providers/** | Абстракция LLM-провайдеров (ProxyAPI, GigaChat) |
| **providers/cache.py** | SQLite-кэш ответов по тексту запроса |
| **vectorstore.py** | FAISS индекс + метаданные документов |
| **retriever.py** | Семантический поиск Top-K документов |
| **pipeline.py** | Координация кэша, поиска и генерации ответа |

### Умный сплиттинг

При индексации текст разбивается так:

1. Сначала по абзацам (`\n\n`)
2. Если абзац длиннее лимита чанка — по предложениям (`. `)
3. Между соседними чанками длинного абзаца — overlap **20%** (хвостовые предложения предыдущего чанка)

Это сохраняет контекст на границах фрагментов при поиске в FAISS.

### Кэширование ответов (SQLite)

- Файл БД: `data/cache.db` (`CACHE_DB_PATH` в `config.py`)
- Ключ — SHA-256 текста пользовательского запроса
- При попадании в кэш пропускаются эмбеддинг, FAISS и вызов LLM
- Статистика: поле `cached_queries` в `/api/stats`

### Журнал взаимодействий (SQLite)

- Файл БД: `data/logs.db` (`LOGS_DB_PATH` в `config.py`)
- Пишется **каждый** запрос к `/api/chat`, включая ответы из кэша и ошибки пайплайна
- Поля: `timestamp`, `session_id`, `query`, `response`, `source`, `from_cache`, `response_time_ms`
- Сбой записи в журнал не ломает ответ пользователю
- Метрики: `/api/logs/stats` (`cache_hit_rate`, `avg_response_time_ms`)
- Экспорт: `/api/logs/export` → `data/logs.csv` (UTF-8 с BOM, корректно открывается в Excel)

### Память диалогов

- До `MAX_HISTORY_LENGTH` пар сообщений (по умолчанию **10 пар** = 20 сообщений)
- История передаётся в LLM вместе с контекстом из базы знаний
- Сессия хранится на сервере по `session_id`; очистка — кнопка 🧹 или `POST /api/clear`
- Очистка истории чата **не** удаляет записи из `logs.db`

### Настройки RAG

В `config.py` или `.env`:

```env
TOP_K_RESULTS=3          # Количество документов для контекста
MAX_CONTEXT_LENGTH=3000  # Макс. длина контекста (символы)
MAX_HISTORY_LENGTH=10    # Пар сообщений в памяти диалога
REQUEST_TIMEOUT=60       # Таймаут запросов к API (сек)
HOST=127.0.0.1
PORT=8000
```

## Решение проблем

### «База знаний не загружена»

Нажмите **📥** в интерфейсе или выполните `POST /api/ingest`.

### Ошибка API

1. Проверьте ключи в `.env`
2. Нажмите **🔌** для проверки подключения
3. Для GigaChat: установите `GIGACHAT_VERIFY_SSL_CERTS=false` при разработке

### Документы не найдены

1. Убедитесь, что `.txt` файлы лежат в `data/docs/`
2. Проверьте кодировку UTF-8

### Смена провайдера

1. Измените `LLM_PROVIDER` в `.env`
2. Перезапустите приложение
3. Выполните индексацию заново (индексы различаются по размерности эмбеддингов)

### Кэш отдаёт устаревший ответ

Удалите файл `data/cache.db` и перезапустите приложение (кэш создастся заново). Журнал `logs.db` при этом сохранится.

### Нужно начать журнал заново

Удалите `data/logs.db` (и при необходимости `data/logs.csv`) и перезапустите приложение.

### Directory 'static' does not exist

Запускайте из `web/` (`python app.py`) или из корня (`python web/app.py`). Пути к `static/` и `templates/` считаются относительно расположения `app.py`.

## Безопасность

- Не коммитьте `.env` с реальными ключами
- Файл `example.env` содержит только шаблон
- Текстовые логи приложения — `app.log` (в каталоге запуска)
- FAISS-индексы, метаданные, `cache.db`, `logs.db` и `logs.csv` в `.gitignore`
